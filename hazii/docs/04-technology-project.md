# Технологический проект Sino

## 1. Назначение и измеримые ориентиры

Sino — веб-приложение для изучения китайского языка: курсы HSK, карточки,
повторение, тренировка письма, прогресс, подписки и администрирование.
Цель первой полной версии — 30–40 тысяч зарегистрированных пользователей.

Количество регистраций не равно количеству одновременных пользователей. Пока
не собрана продуктовая статистика, проектируем систему под 40 000
зарегистрированных, 5 000 дневных активных, до 500 одновременных сессий и до
50 запросов чтения в секунду в пике. Перед коммерческим запуском эти цифры
обязательно уточняются нагрузочным тестом.

| Требование | Ориентир первой версии |
|---|---|
| Доступность учебного интерфейса | 99,5% в месяц |
| Обычный API-ответ | 95% ответов до 400 мс |
| Резервные копии | ежедневно; восстановление проверяется раз в квартал |
| Статика | CDN, сжатие, кеширование |
| Безопасность | HTTPS, аудит действий администратора, нет секретов в Git |

## 2. Архитектурный подход

Сразу определяем границы **логических микросервисов**, но не запускаем десять
независимых серверов в первый день. Для небольшой команды это создаст больше
сложности, чем пользы. Первые сервисы могут жить в одном монорепозитории и
одном кластере, однако у каждого сервиса будет собственный API, миграции,
роль БД и владелец данных.

Это важно: сервис не читает таблицы другого сервиса напрямую. Он вызывает его
API или получает опубликованное событие. Благодаря этому нагруженный сервис
можно потом выделить без переписывания всего продукта.

```text
Браузер (React)
       │ HTTPS
       ▼
CDN / WAF / балансировщик
       │
       ▼
API Gateway / BFF ────────► Identity Service
       │                    Catalog Service
       │                    Learning Service
       │                    Billing Service ──► платёжный провайдер
       │                    Admin Service
       │                    Notification Service
       │
       ├──────────────► PostgreSQL (отдельные схемы и роли)
       ├──────────────► Redis
       ├──────────────► NATS JetStream
       └──────────────► S3-совместимое хранилище

Worker Service ◄──────── события из NATS
       ├──────────────► email / push-провайдер
       └──────────────► аналитическое хранилище
```

`API Gateway / BFF` — единственный публичный серверный API для браузера.
Он проверяет сессию, объединяет ответы внутренних сервисов и не раскрывает
внутренние адреса базы, очередей и сервисов.

## 3. Сервисы

| Сервис | Ответственность | Владеет данными | Ключевые события |
|---|---|---|---|
| Identity | OAuth-вход, сессии, роли, блокировки | пользователи, OAuth-связи, сессии, роли | `user.created`, `user.blocked` |
| Catalog | HSK, курсы, уроки, слова, иероглифы, источники | учебный каталог | `catalog.version.published` |
| Learning | уроки, прогресс, интервальное повторение, учебные сессии | прогресс, review-карточки, сессии | `lesson.completed`, `review.completed` |
| Writing Check | проверка траектории письма | правила проверки, результаты попыток | `writing.checked` |
| Billing | товары, цены, заказы, подписки, права доступа | платежи, права доступа, webhook | `payment.succeeded`, `entitlement.changed` |
| Notification | напоминания и история доставок | настройки, задания, доставки | `notification.sent` |
| Admin & Analytics | служебный API, аудит и отчёты | аудит и агрегированные проекции | `admin.action.logged` |
| Worker | очередь, пересчёты, отправки, дедупликация | только технические задания | потребляет события |

`Writing Check` допустимо начать как модуль Learning Service. Его стоит
выносить в отдельный процесс только если проверка потребляет много CPU или
за неё отвечает отдельная команда.

## 4. Технологии

| Слой | Решение | Причина |
|---|---|---|
| Web | React + Vite + React Router | текущий проект уже использует React; быстрая разработка |
| Язык | JavaScript на учебном фронтенде, TypeScript для production-сервисов | сначала проще учиться, затем больше проверок кода |
| UI | CSS variables, собственные компоненты, позже Storybook | единая пастельная дневная и ночная тема |
| Backend | Node.js LTS + TypeScript + NestJS на Fastify | один язык, понятная структура модулей и быстрый HTTP |
| HTTP-контракты | OpenAPI | фронтенд и сервер заранее знают форму запросов |
| Основная БД | PostgreSQL 16+ | связи, транзакции, подписки, надёжные индексы |
| Кеш и rate limit | Redis | кеш каталога, короткие блокировки, лимиты входа |
| События | NATS JetStream | надёжные фоновые задачи и повторная доставка |
| Файлы | S3-совместимое объектное хранилище | аудио, иллюстрации, траектории письма, экспорты |
| Наблюдаемость | OpenTelemetry, Prometheus, Grafana, Loki, Sentry | ошибки, метрики, логи, трассировка |
| Инфраструктура | Docker Compose локально; Docker + managed containers/Kubernetes в production; Terraform | воспроизводимый запуск |
| CI/CD | GitHub Actions или GitLab CI | тесты, сборка, миграции, развёртывание |

Для персональных данных и платежей понадобится инфраструктура с дата-центрами
в России, договором обработки данных и регулярными резервными копиями.
Соответствие законодательству, онлайн-касса и пользовательские документы
перед коммерческим запуском подтверждаются юристом и бухгалтером.

## 5. Будущая структура репозитория

Текущая папка `hazii` остаётся учебным React-проектом. С появлением сервера
она развивается в монорепозиторий:

```text
hazii/
├── apps/
│   ├── web/
│   ├── gateway/
│   ├── identity-service/
│   ├── catalog-service/
│   ├── learning-service/
│   ├── billing-service/
│   ├── notification-service/
│   ├── admin-service/
│   └── worker/
├── packages/
│   ├── ui/             # общие React-компоненты
│   ├── contracts/      # OpenAPI и форматы событий
│   ├── config/         # проверка настроек окружения
│   └── test-fixtures/  # тестовые данные
├── infra/              # Docker, Terraform, production-конфигурация
└── docs/
```

Секреты не хранятся в Git. OAuth-ключи, платёжные ключи и пароли БД приходят
на сервер через менеджер секретов и переменные окружения.

### Правило многосложного слова и скрытого иероглифа

Если слово состоит из трёх иероглифов, сервер создаёт три задачи с позициями
`1`, `2`, `3`. В тестовом режиме браузер получает только непрозрачный ID текущей
задачи и чистое поле для письма, но не ожидаемый символ и не эталонные черты.
После отправки траектории сервер возвращает только результат и наличие следующей
задачи:

```json
{ "result": "correct", "nextTaskAvailable": true, "completedCount": 1, "totalCount": 3 }
```

После подтверждения поле очищается и открывается следующая задача. Подсказка —
отдельный учебный режим, а не случайное раскрытие ответа в тестовом режиме.

## 8. API и события

Внешние запросы используют `/api/v1/...`; входящие тела валидируются по
схеме, а каждый ответ содержит `requestId` для поиска ошибок в логах.

| Метод и путь | Сервис | Действие |
|---|---|---|
| `POST /api/v1/auth/oauth/:provider/start` | Identity | начать OAuth-вход |
| `POST /api/v1/auth/refresh` | Identity | обновить сессию |
| `GET /api/v1/me` | Gateway | профиль, роли, права доступа |
| `GET /api/v1/courses` | Catalog | каталог HSK |
| `GET /api/v1/lessons/:id` | Catalog | опубликованный урок |
| `POST /api/v1/study-sessions` | Learning | начать сессию |
| `GET /api/v1/practice-sessions/:id/current-task` | Learning | выдать закрытую задачу |
| `POST /api/v1/practice-tasks/:id/attempts` | Writing/Learning | проверить траекторию |
| `GET /api/v1/reviews/queue` | Learning | очередь повторения |
| `POST /api/v1/checkout` | Billing | создать заказ, вернуть URL оплаты |
| `POST /api/v1/webhooks/yookassa` | Billing | принять серверное уведомление |
| `POST /api/v1/admin/entitlements/grants` | Admin/Billing | выдать ручной доступ с аудитом |

У каждого события есть `eventId`, `occurredAt`, `schemaVersion` и
`correlationId`. Потребители событий должны быть идемпотентными: повторное
уведомление не может второй раз открыть подписку или отправить два письма.

## 9. Подписки и СБП

1. Пользователь выбирает тариф; браузер вызывает Billing Service.
2. Billing создаёт внутренний заказ `pending` и передаёт провайдеру ключ
   идемпотентности.
3. Браузер получает только URL подтверждения и перенаправляет пользователя.
4. Возврат на `/billing` **не открывает** премиум-функции.
5. Провайдер присылает серверное HTTPS-событие `payment.succeeded`.
6. Billing сохраняет webhook, защищается от повтора, при необходимости
   сверяет статус через API провайдера и в одной транзакции создаёт подписку и
   право доступа.
7. Событие `entitlement.changed` сбрасывает кеш прав пользователя.

ЮKassa документирует API приёма платежей и webhook-уведомления о смене статуса
платежа. URL webhook должен быть HTTPS. Условия СБП, фискализации и возможных
рекуррентных списаний нужно подтвердить с выбранным провайдером непосредственно
перед интеграцией.

## 10. Ограниченные права администраторов

```text
users.read              — искать пользователей
users.block             — блокировать и разблокировать
billing.read            — просматривать платежи
billing.manage          — выдавать/отзывать доступ, оформлять возврат
catalog.manage          — менять и публиковать учебные материалы
analytics.read          — смотреть агрегированные отчёты
admins.manage           — назначать ограниченные роли
audit.read              — просматривать журнал действий
```

Каждое административное действие сохраняет исполнителя, время, объект,
безопасное «до/после», причину и `requestId`.

## 11. Безопасность и запуск

- OAuth callback проверяет `state`, PKCE и точный redirect URI.
- Refresh-сессия хранится в защищённой HTTP-only cookie; access-токены короткие.
- Логи маскируют email, токены, cookie и платёжные реквизиты.
- Redis ограничивает частоту попыток входа, API и webhook.
- У сервисов отдельные роли БД и минимально необходимые права.
- До production нужны: проверка OAuth, threat modeling, нагрузочный тест,
  тест восстановления БД и сценарий повторной доставки webhook.

## 12. Порядок реализации

1. Учебный фронтенд: HSK 1 из тестовых данных, маршруты, карточка слова,
   дневная/ночная тема.
2. PostgreSQL и Catalog: миграции, import-пайплайн, лицензии источников.
3. Identity и Learning: OAuth, сессия, прогресс, SRS.
4. Письмо: canvas, закрытые задачи, проверка и качество попыток.
5. Billing: тестовый платёжный контур, webhook, права доступа, ручная выдача.
6. Notification и Admin: цели дня, напоминания, роли, аудит, отчёты.
7. Production readiness: мониторинг, бэкапы, нагрузка, документы, развёртывание.
