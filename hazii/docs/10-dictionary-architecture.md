# Словарь БКРС: данные и работа под нагрузкой

## Что хранится сейчас

Словарь — самостоятельная часть Sino. Он не зависит от HSK-курсов и не меняет учебный прогресс пользователя.

В локальную базу импортированы статические данные из переданного файла БКРС версии `250314`:

- китайско-русское направление: 3 399 298 карточек;
- русско-китайское направление: 254 053 карточки;
- всего: 3 653 351 словарная статья.

Каждая статья сохраняет слово, пиньинь (когда он есть), полный текст статьи и примеры, которые находятся в статье. Отдельно сохраняются направление и версия источника. Повторный импорт заменяет только статьи этого источника, не затрагивая учебные данные пользователя.

Перед публикацией нужно получить подтверждение условий использования и распространения данных БКРС у правообладателя. Техническая возможность импорта не равна разрешению на коммерческое использование.

## Как проходит один поиск

```text
Поле поиска в браузере
        │  (пауза 220 мс)
        ▼
GET /api/dictionary/search
        │  (короткие подсказки: слово, пиньинь, превью)
        ▼
Redis-кэш ──► PostgreSQL dictionary.entries
        │
        ▼
Плитки с вариантами под полем ввода
        │  (пользователь выбирает одну плитку)
        ▼
GET /api/dictionary/entries/:id
        │  (одна полная статья)
        ▼
Модальное окно со значениями и примерами из исходной статьи
```

Браузер не подключается к PostgreSQL и не получает полный текст всех найденных статей. Это не только быстрее: так меньше данных передаётся при каждом нажатии клавиши.

## Части кода

| Место | Ответственность |
| --- | --- |
| `src/features/dictionary/DictionaryPage.jsx` | Поле поиска, подсказки и плавно закрывающееся окно одной статьи. Здесь нет SQL и нет привязки к HSK. |
| `api/server.mjs` | Два HTTP-маршрута, нормализация запроса, безопасный лимит выдачи и кэширование. |
| `infra/postgres/init/03-dictionary-schema.sql` | Отдельная схема `dictionary`, статьи, сведения об источнике, журнал импортов и поисковые индексы. |
| `scripts/importBkrsDictionary.mjs` | Безопасно читает статическую выгрузку, загружает её во временную таблицу и только затем заменяет старую версию. |

Полная статья показывается без придумывания или сокращения: интерфейс выводит весь текст из поля `article`. Поэтому примеры, варианты перевода и пометы видны ровно там, где они есть в переданной версии БКРС; статьи без примеров не дополняются искусственно.

## Поиск

Для быстрых ответов база использует три типа индексов:

- точное совпадение и поиск по началу китайского слова;
- поиск по пиньиню;
- полнотекстовый поиск по русскому содержимому статьи.

Клиент запрашивает не более 24 результатов, не отправляет пустые запросы и ждёт 180 мс после последнего введённого символа. Это снижает лишнюю нагрузку при быстром наборе текста. Часто повторяемые запросы на пять минут сохраняются в Redis и разделяются между экземплярами API; при недоступности Redis поиск безопасно продолжается через PostgreSQL.

## Путь к высокой нагрузке

Фраза «5000 тыс. человек» может означать до 5 000 000 одновременных посетителей. Для такой величины нельзя рассчитывать на один сервер или одну базу данных. Текущая реализация — корректное ядро данных для локального запуска и раннего MVP; производственная схема должна развиваться по этапам.

1. **До нескольких тысяч одновременных пользователей.** Несколько одинаковых экземпляров API за балансировщиком, PostgreSQL с репликой для чтения, Redis для кэша популярных запросов, CDN для фронтенда.
2. **Десятки тысяч одновременных пользователей.** Выделенный поисковый кластер (OpenSearch или Typesense) с индексом словаря; PostgreSQL остаётся источником истины. Подключается пул соединений PgBouncer, мониторинг, ограничение частоты запросов и резервные копии.
3. **Сотни тысяч и миллионы одновременных пользователей.** Горизонтально масштабируемый поисковый кластер, шардирование, несколько регионов доставки, отдельные очереди для импорта и аналитики, нагрузочное тестирование и план аварийного восстановления.

Полный импорт БКРС должен выполняться отдельно от веб-запросов: сначала загружаться во временную таблицу, затем атомарно становиться новой версией. Пользователь никогда не видит «половину» словаря.

## Важные показатели

Перед запуском нужно измерить: p95-время поиска, число запросов в секунду, попадания в кэш, нагрузку на базу, ошибки API и скорость автоподсказок. Целевой ориентир для экрана поиска — ответ до 300 мс в 95% запросов из России.
